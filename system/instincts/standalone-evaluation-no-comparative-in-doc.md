## Pattern

This is distinct from `prefer-chat-synthesis-during-iteration` (which is about output format during real-time iteration — chat vs. doc). This instinct is about **content scope within a durable evaluation artifact** — what belongs in the doc and what stays in chat.

**Likely reasons for the pattern:**

1. **Absolute-bar evaluations don't drift.** Comparative evaluations age fast — when the next candidate joins the loop, the comparison table is stale. Absolute-bar reads survive.
2. **Comparative framing risks normalization.** Saying "this candidate is weaker than X but stronger than Y" can read as "third-best of four" instead of "doesn't clear the bar." For Lean No candidates especially, the absolute-bar frame is more honest.
3. **The hiring doc is the durable record consumed by future Leo (or James) without context.** A future re-read shouldn't depend on knowing who the other 4/16-loop candidates were. The doc must be self-contained.
4. **Comparative framing belongs in a separate "loop assessment" memo if needed**, not in per-candidate files.

**Heuristics for when this fires:**

1. Writing a new hiring evaluation file → keep it standalone, no comparison table to other candidates
2. Writing a stakeholder profile → keep it standalone, no comparison to other stakeholders
3. Writing a project assessment → keep it standalone, no comparison to other projects in the portfolio
4. **Comparative framing in chat is fine** — that's where Leo's analysis lives; the doc is the artifact

**What Leo should do instead:**

- In chat: compare freely, surface tradeoffs, call out where this evaluation differs from prior ones
- In the doc: evaluate against absolute role bar / success criteria; cite specific behaviors / artifacts / outcomes; use "discriminator" or "what would flip the read" framing rather than "vs. other candidates"
- If comparison genuinely matters for the decision, put it in a separate file or in chat synthesis, not in the candidate file
