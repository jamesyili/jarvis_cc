Part 1Your questions so far — and a tight consolidation of what's taught

The two Q (James) blocks from llm_fundamentals.md, answered fresh + consolidated, then a one-pass recap of self-attention / multi-head / the block so it's all in one place.

Q (James) · #1 — logged
Why do transformers work for recsys too — is it the sequential part? And why are transformers tied to "scaling"?

Not mainly the sequential part. Sequential recommendation (history → next item, SASRec/BERT4Rec) is the common case, but it's not why attention wins. The win is three mechanisms — and only the third is about sequences:

  1. Direct long-range access. An RNN crushes all history into one fixed hidden state that decays over steps. Attention reads any past interaction directly — path length 1, with a learned weight. A guitar video from 3 months ago can still fire for the right candidate.
  2. Content-dependent dynamic weighting. Each past item's relevance is computed from content (Q·K), so the user representation re-shapes per candidate — camping history up-weights before a tent, fashion before a handbag (your worked example). Pooling can't: its weights are fixed.
  3. Parallelism. RNNs are sequential (t needs t−1); transformers compute all positions at once → you can actually train on billion-row interaction logs.

Deepest framing (worth memorizing): attention is learned, content-dependent aggregation over a set with explicit pairwise interactions. Sequences are one instance; the same operator does feature-interaction modeling and candidate-set modeling too (Part 3).

Scaling = scaling laws. Transformer test loss falls as a clean power law in params / data / compute over many orders of magnitude (Kaplan 2020 → Chinchilla 2022) — predictably, so you can forecast a bigger model's quality before training it. Why transformers, specifically, scale:

  • No saturating bottleneck. Unlike an RNN's fixed state or a CNN's fixed receptive field, all-to-all attention means added width/depth/heads always have something to do — no dead capacity.
  • Parallelism delivers the scale. Turns more compute into more throughput; RNNs structurally can't.
  • Self-supervision removes the data ceiling. Next-token (next-item) needs no labels → the data axis is ~unlimited.
The one-sentence unification: a single property — all-to-all attention + parallel computation — pays off twice. All-to-all access gives both long-range recsys modeling and bottleneck-free scaling; parallelism makes both huge recsys logs and huge pretraining feasible.
Q (James) · #2 — logged
What do Q/K/V and the W matrices represent in recsys? Does every item have an ID embedding, and what about cold-start (OOV/OOC)?

Q/K/V roles: Query = "what am I looking for" (the prediction context — most recent item, or the candidate being scored). Key = "what do I match against" (each past item's advertised index — controls whether it's attended to). Value = "what I contribute" (the content that flows once attended — controls what flows). The crux: key and value are different learned projections of the same item, so the geometry you match on is decoupled from the content you pass. Continuity with two-tower: it's the same dot-product relevance, but applied inside the history and recomputed per context.

The W matrices (WQ/WK/WV) are the learned projections that define query/key/value. They're shared across all positions — one WQ for every item — so sequence length adds zero parameters. WK/WQ carve the matching subspace; WV carves the content subspace. (Alammar's 64-vs-512 is just the multi-head split: d_k = d_model/h = 512/8 = 64; 8 heads × 64 ≈ one 512-wide head's cost.)

ID embeddings + cold-start. Vanilla SASRec/BERT4Rec keep a per-item-ID lookup table (= the token table; vocabulary = catalog). That gives the OOV problem in two flavors: (1) cold-start — an unseen item has no trained row; (2) long-tail starvation — rare IDs are barely trained, and the table is enormous. Fixes, usually combined:

  • Content/feature embeddings (image / text / category → encoder): a new item has content even with zero interactions, so it generalizes to unseen — this is why OmniSage-style content embeddings exist. The main fix.
  • Hashing trick: hash any ID into fixed buckets → unseen IDs still land somewhere (lossy, via collisions).
  • Hybrid (industry default): ID embedding (sharp CF/memorization for the head) ⊕ content embedding (generalization for tail + cold); warm up the ID online once interactions accrue.
The precise NLP parallel (good interview line): NLP killed OOV with subword/BPE — unseen words decompose into known sub-units. Recsys can't (an item doesn't decompose into "sub-items"), so it escapes through content features instead. Same problem, different hatch — because of what an "item" is versus a "word." This is also exactly why tokenization (your roadmap item #1) has no clean recsys analogue — see Part 2, Q-D.

Consolidation — what you've already been taught, in one pass

Self-attention. Stack tokens into X (n×d). Project three ways: Q=XW_Q, K=XW_K, V=XW_V. Then:

Attention(Q,K,V) = softmax( Q·Kᵀ / √d_k ) · V
  • Q·Kᵀ → (n×n) raw scores; entry (i,j) = how much token i should pull from token j.
  • /√d_k → dot products grow like √d_k; unscaled, softmax saturates (one weight≈1) and its gradient ≈0 → training stalls. Scaling holds variance ~1. That's the only reason this term exists.
  • softmax (per row) → each token's scores become a distribution over "where it looks."
  • ·V → weighted average of value vectors. Weights are recomputed from content every forward pass — not fixed.
  • Causal mask: set scores (i,j) with j>i to −∞ before softmax → token i sees only itself + earlier. Makes left-to-right next-token (next-item) training well-posed.

Your pooling-vs-attention worked example nailed the payoff — same 5-item history, three results:

AggregationUser vector [camping, cooking, fashion]Behavior
Pooling (uniform)[0.43, 0.20, 0.42]Identical for everything — can't adapt
Attention · scoring a tent[0.59, 0.16, 0.34]Camping-forward
Attention · scoring a handbag[0.34, 0.13, 0.57]Fashion-forward

Same history, different representation per context — weights are a function of the query, recomputed every forward pass.

Multi-head: one head = one averaged mixture, so distinct patterns (adjacency, coreference, subject–verb) interfere. Split into h heads of width d/h, run attention independently, Concat·W_O. ≈ same compute as one wide head, but h independent patterns. Heads specialize empirically (observed, not enforced).

The block (pre-norm, decoder-only):

z = x + MultiHeadSelfAttn(LayerNorm(x)) y = z + FFN(LayerNorm(z))

Attention sublayer = the only cross-position mixing. FFN sublayer = per-token processing, W₂·φ(W₁·u+b₁)+b₂, hidden ≈ 4d, where most params + stored knowledge live. Residual = learn a delta + gradient highway. LayerNorm = keep activations well-conditioned. Stack L blocks; lower layers → local/syntactic, higher → abstract/semantic (emergent).

Part 2Likely next questions — straight off your roadmap

Q-A · roadmap #6, "next"
Positional encoding — if attention is a weighted average, it's order-blind. How is order injected, and what's RoPE?

Correct: pure self-attention is permutation-equivariant — shuffle inputs, outputs shuffle identically. Position must be added explicitly.

Original (sinusoidal, absolute): add a fixed vector to each token embedding,

PE(pos, 2i) = sin( pos / 10000^(2i/d) ) PE(pos, 2i+1) = cos( pos / 10000^(2i/d) )

Each dimension is a sinusoid of a different wavelength. Two virtues: extends past training lengths, and sin/cos shift identities let the model express relative offsets linearly.

RoPE (Rotary Position Embedding) — the modern default in LLMs. Instead of adding a position vector, rotate the query and key vectors by an angle proportional to position (rotate dimension-pair i by pos·θ_i). The dot product q_i·k_j then depends only on the relative offset (i−j), not absolute positions. Why it won: relative position falls out naturally, it's applied at every layer inside attention, and it extrapolates to longer contexts better. ALiBi is the simpler cousin — just add a distance-proportional penalty to attention scores, no embeddings at all.

RecSys twist: position ≈ time, and time is a real feature, not just order. Recency and absolute time-gaps carry signal (a purchase 1 hour ago ≠ 1 year ago). So recsys sequence models often inject timestamps / time-gap embeddings, not just ordinal position — and RoPE-style relative schemes map naturally onto "how long ago." This is a genuine divergence from NLP, where position is purely ordinal.
Q-B · roadmap #7, todo
Training objective — what exactly does next-token prediction optimize, and how can the decoder train in parallel if generation is sequential?

Objective: minimize cross-entropy of the predicted next-token distribution against the actual next token, summed over every position. The final hidden vector per position → linear-to-vocab ("unembedding," often weight-tied to the input table) → softmax → P(next token). Loss = −Σ_t log P(x_t | x_{<t}). That's it; pretraining is just this at scale.

Why parallel training works — teacher forcing. At train time you already have the whole target sequence, so you feed it in at once; the causal mask guarantees position t only sees <t. You compute the loss at every position in one forward pass. Generation is sequential only at inference, where the future doesn't exist yet. This parallel-train / sequential-infer asymmetry is a big reason transformers were trainable at scale.

RecSys twist — this is where it gets hard. The "vocabulary" is the item catalog (millions–billions, changing daily). A full softmax over all items every step is impossible. So recsys uses sampled softmax / negative sampling: score the true next item against a small set of sampled negatives (in-batch + popularity-sampled), with a logQ correction for the sampling bias. (Same trick word2vec used, scaled up.) Replication finding worth knowing: SASRec, when trained with full/sampled softmax rather than a single-negative BPR loss, often matches or beats BERT4Rec — i.e. the loss and negative sampling frequently matter more than the encoder-vs-decoder choice. Good thing to say when someone fixates on architecture.
Q-C · roadmap #8, todo
Decoding / inference — how does generation actually run, and what's the KV-cache?

Generation is autoregressive: predict token, append it, feed back, repeat. Selection = greedy (argmax), sampling (temperature / top-k / top-p), or beam search.

KV-cache: naively, generating token t recomputes attention over all t−1 prior tokens — and their keys/values never change. So you cache past K and V and only compute Q/K/V for the new token. This turns per-step cost from O(t²) to O(t) and is the single most important inference optimization. The cost: the cache grows linearly with sequence length × batch and usually becomes the memory bottleneck at serving (it's why MQA/GQA — sharing K/V across heads — exist).

RecSys twist — serving is structurally different. You almost never autoregressively decode item-by-item in production. Instead: a transformer encodes the user's history into one user embedding, which is matched against precomputed item embeddings via approximate nearest neighbor (ANN: HNSW/ScaNN/FAISS) — sub-linear, no softmax, no decode loop. Even better, PinnerFormer-style models compute the user embedding offline/daily in batch so request-time serving is just an ANN lookup. The KV-cache is an LLM-decode concern; recsys's analogous concern is the ANN index + embedding store (Part 3).
Q-D · roadmap #1, open
Tokenization / BPE — and why does recsys not really have it?

BPE (byte-pair encoding): start from characters, iteratively merge the most frequent adjacent pair into a new token, build a vocab of ~30–250k subwords. Result: common words are one token, rare words split into known sub-units, and there's no OOV — anything decomposes into pieces (worst case, bytes).

Why recsys can't do this (ties back to your Q#2): a word has internal structure (morphemes, characters) to decompose into; an item does not decompose into "sub-items." So recsys can't tokenize its way out of OOV — it escapes via content features instead. Unless you manufacture decomposability artificially — which is exactly what semantic IDs do (Part 3, Q-G): learn a short code-sequence per item so items do share sub-units. That's the bridge that lets the newest recsys models borrow BPE-style generation.

Q-E · the "why" behind it all
Quantify "long-range is easier." And when do I pick encoder vs decoder (BERT4Rec vs SASRec)?

The complexity table worth memorizing — path length = steps a signal traverses to connect two positions (shorter = easier long-range learning):

LayerCompute / layerSequential opsMax path length
Self-attentionO(n²·d)O(1)O(1)
RecurrentO(n·d²)O(n)O(n)
ConvolutionO(k·n·d²)O(1)O(log_k n)

Self-attention's O(1) path length is the reason it beat RNNs. The price is O(n²) in sequence length — which directly caps how long a user-history you can afford, and is why "efficient attention" (sparse/linear/FlashAttention) exists.

The encoder/decoder fork maps cleanly onto your two recsys models:

TypeAttentionNLPRecSysObjective
Decoder-onlyCausalGPTSASRecNext-item (autoregressive)
Encoder-onlyBidirectionalBERTBERT4RecCloze: mask items, predict from both sides

Rule of thumb: causal/SASRec maps naturally to streaming, online next-item serving; bidirectional/BERT4Rec can be stronger offline because it uses two-sided context — but see Q-B: the loss often dominates the choice.

Q-F · the production shape
Where does the transformer actually sit in a real two-stage system?
billions of items
↓   RETRIEVAL — cheap, high recall
Two-tower retrieval
user tower = Transformer over history → u
item tower = item / content features → i
score = u · i → ANN search (HNSW)
↓   ~hundreds of candidates
Ranking — heavy model (often Transformer)

+ feature-interaction attention
→ calibrated P(click / save / conversion)
↓   ~tens

Key insight: the transformer's expense scales with where you put it. In retrieval it encodes the user once and stays light (item side precomputed offline for ANN — and "transformer = the user tower over history" is the workhorse, continuous with the two-tower framing you already know). In ranking you can afford richer per-candidate attention because you're scoring only a few hundred.

Q-G · Pinterest-relevant anchor
Give me one concrete industrial model I can reason about directly.

PinnerFormer (Pinterest, 2022) — the on-point reference for your world:

  • A transformer over the user's Pin-action sequence produces one long-term user embedding for retrieval.
  • Signature contribution: the "dense all-action" loss — predict the user's engagement over a multi-day future window rather than only the immediate next action. Shifts the embedding from chasing the next click toward durable long-term interest, and lets it be computed offline/daily in batch (huge serving-cost win; ties straight to Q-C).
  • Don't conflate with PinnerSage — that's an earlier clustering/multi-embedding approach, not a transformer. PinnerFormer is the transformer/sequence one. Content embeddings here connect to the OmniSage-style features you noted for cold-start.

Broader industry pattern (Pinterest, Meta, Alibaba, YouTube) is identical: transformer over user action sequence → user embedding → retrieval and/or ranking. That's the one sentence to leave the plane with.

Q-H · attention in ranking
Sequence models cover history. Does attention also help model feature interactions in the ranker?

Yes — same operator, different "sequence." Here the set is the feature fields (user_age, item_category, device, hour…), each an embedding, and self-attention learns high-order feature interactions automatically instead of hand-crafted crosses.

  • AutoInt (2019): multi-head self-attention over feature-field embeddings for CTR. Replaces the FM / Wide&Deep manual-cross labor.
  • DIN → DIEN (Alibaba, 2018): the direct ancestor of attention-in-ranking. Target attention — given a candidate item, attend over the user's history weighted by relevance to that candidate. This is structurally the decoder's cross-attention: candidate = query, history = keys/values. (DIEN adds a GRU for interest evolution.) This predates full transformers in recsys and is why "attention" was in ranking before "transformer" was.

So transformers appear in both stages: as sequence encoders (history → user embedding) in retrieval, and as target-attention / feature-interaction models in ranking.

Q-I · the frontier
What's beyond "transformer as encoder"? Where is this heading?

Generative retrieval: instead of "encode user → ANN over item vectors," generate the item ID directly, exactly like an LLM emits tokens.

  • Semantic IDs + TIGER (Google, 2023): represent each item as a short sequence of discrete codes (a "semantic ID," learned via a quantizer like RQ-VAE over content embeddings), then train a seq2seq transformer to generate the next item's semantic ID autoregressively. Retrieval becomes decoding — no ANN index — and items that share codes generalize (cold-start relief). This is the artificial decomposability from Q-D that lets recsys borrow BPE-style generation.
  • Generative recommenders / scaling laws (e.g. Meta's HSTU, 2024): recast retrieval + ranking as one large generative sequence task to inherit transformer scaling-law behavior — the bet that the LLM scaling recipe (your Q#1) transfers to recsys.

The strategically literate take: recsys is being re-cast as a sequence-generation problem. That's the natural endpoint of "transformers for recsys," and where your Q#1 scaling-laws thread and Q#2 cold-start thread converge.

Deep dive · addedPinterest TransAct — v1 → v2

This is everything in Part 3 made concrete in your own building. TransAct is the realtime user-action transformer that lives inside Pinnability, Pinterest's Homefeed ranking model. v1 (KDD 2023) introduced it on short realtime sequences; v2 (CIKM 2025) extended it to lifelong sequences, added a next-action objective, and solved the serving problem. Read v1 as "how a transformer plugs into a pointwise ranker," and v2 as "how you make that work at O(10⁴) history length."

TransAct v1 — realtime short-term interest in the ranker

TA1 · where it sits
What's the host model, and how does TransAct plug in?

The host is Pinnability — a Wide & Deep ranker: features go through DCN v2 explicit feature-crossing, then an MLP, then multi-task heads predicting each engagement type (repin/save, click, hide, …) with a weighted cross-entropy. TransAct is a submodule: it consumes the user's realtime action sequence, produces a compact representation, and that vector is concatenated into the input of the DCN v2 crossing layer alongside all the other features. It doesn't replace the ranker — it's a sequence encoder bolted onto it.

Hybrid short-term ⊕ long-term. TransAct (realtime, last-100 actions, short-term intent) runs alongside PinnerFormer (the batch/daily user embedding from Part 3, long-term interest). Ablations quantify the split: removing TransAct costs −8.59% HIT@3/repin; removing PinnerFormer costs −2.46%. Translation: for Homefeed ranking, fresh realtime short-term signal matters ~3.5× more than the batch long-term embedding — the strategic reason v1 existed at all.

TA2 · the core idea
What's the one architectural trick that makes it work — and how does it relate to DIN target attention?

Candidate early-fusion. Each of the user's most recent 100 actions becomes a token = [ PinSage pin embedding (32-d) ⊕ action-type embedding (32-d) ]. The crucial move: the candidate pin's PinSage embedding is concatenated onto every action token before the transformer runs. So self-attention is computed in a representation that already "knows" what's being scored — the model learns how each past action relates to this specific candidate.

This is DIN's target attention (Part 3, Q-H) realized through early fusion + self-attention. DIN explicitly attends history → candidate; TransAct injects the candidate into each token and lets ordinary self-attention discover the candidate-conditioned relevance. Same goal (candidate-aware history aggregation), cleaner mechanism, and it composes with multi-head self-attention's other benefits.

Encoder config (deliberately tiny): 2 layers, 1 attention head, feed-forward dim 32, and — notably — no positional encoding (they tested it; it didn't help, since action-type + the recency structure already carry what's needed at length 100). A reminder that "production transformer" ≠ "giant transformer."

TA3 · the masking trick
What's the request-time random time-window mask, and why does it exist?

During training only: sample a window T ~ Uniform(0, 24h) and mask every action in (t_request − T, t_request) — i.e. randomly hide the most-recent slice of history. Two reasons, both important:

  • Train/serve skew. Realtime features have ingestion lag, so at serving the very latest actions may not be available. Random masking during training makes the model robust to that missing tail instead of depending on it.
  • Diversity / anti-"rabbit hole." Without it the model over-fixates on the single most recent action and collapses the feed (you click one camping pin → all camping). Masking keeps it from over-weighting recency. Net effect: diversity drop held to −1% with no loss in relevance.
TA4 · output + serving
How is the transformer output compressed, and how do they afford it at serving?

Output aggregation: take the transformer's output columns, concatenate the first K=10 positions with a max-pool over all positions, flatten, and feed that fixed vector into DCN v2. (Cheaper and as effective as using the full output.)

Serving: adding the transformer was a ~65× compute increase over the prior ranker. Made affordable via GPU serving, kernel fusion (nvFuser + custom cuCollections hash tables), coalescing hundreds of small tensor copies into one buffer, CUDA Graphs, larger batches, and mixed precision. This is the practical face of the O(n²) cost flagged in Part 2, Q-E.

TransAct v2 — lifelong sequences, a next-action objective, and the serving fix

TA6 · motivation
What three gaps in v1 (and industry CTR models) does v2 close?
  1. Sequences too short. v1 used O(10²) recent actions, so it captured short-term intent but missed long-term behavior. v2 goes lifelong.
  2. No prediction signal. The ranker only encodes actions; it never learns to predict the next one. v2 adds the Next Action Loss.
  3. No serving story for long sequences. Naively feeding O(10⁴) actions is infeasible; v2 ships an end-to-end low-latency solution.
TA7 · lifelong sequences
How do you use ~16k actions in a transformer that only wants a couple hundred?

Lifelong (LL) sequence: up to O(10⁴) actions (~16k — the 90th percentile of a user's past 2 years), explicit engagements only (repins/clicks/hides; impressions excluded). Each token: timestamp, action type (multi-hot), surface, 32-d PinSage embedding.

The key idea — candidate-relative nearest-neighbor selection inside the sequence. You don't run the transformer over all 16k. You first retrieve the most relevant slice with respect to the candidate:

S_all = NN(S_LL, c) ⊕ S_RT[:r] ⊕ NN(S_RT[r:], c) ⊕ NN(S_imp, c) NN(S, c) = top-K by argsort( PinSage(S) · e_c ) ← dot-product to candidate c
  • NN(S_LL, c) — top-K lifelong actions most similar to the candidate (the long-term, candidate-relevant memory).
  • S_RT[:r] — the most recent r realtime actions, kept regardless of similarity (preserve recency).
  • NN(S_RT[r:], c) and NN(S_imp, c) — candidate-relevant picks from older realtime + from impressions.

The concatenation is compressed back to O(10²) (≈192 tokens optimal) before the transformer. This is ANN retrieval (Part 3, Q-F) applied inside the user's own history — a "retrieve-then-attend" pattern that lets a small transformer see two years of behavior. Storage is halved by quantizing PinSage fp16 → int8 (affine, scale 0.65).

TA8 · Next Action Loss
What is NAL, and why bolt a prediction task onto a pointwise ranker?

NAL is an auxiliary self-supervised task: from the transformer's user embedding u(t) at time t, predict the user's next positively-engaged pin p(t+1) via sampled softmax:

L_NAL = −log e^⟨u(t), p⁺⟩ / ( e^⟨u(t), p⁺⟩ + Σ_neg e^⟨u(t), n⟩ )
  • Positives: future tokens with positive engagement.
  • Negatives: impression-based (pins the user saw but didn't engage) beat in-batch random negatives — they're a harder, more informative contrast (learns nuanced disinterest). Same lesson as Part 2, Q-B: negatives matter.
  • Causal masking prevents leakage from the future.
  • Combined objective: L = L_CE + w_NAL · L_NAL, with w_NAL = 0.01.
Why it works: it imports the next-token (next-item) generative objective from Part 2, Q-B into an otherwise purely discriminative pointwise ranker. The auxiliary "what comes next" signal forces a richer user representation than click/no-click labels alone can teach. Architecture for v2: 2 layers, dim 64, 1 head, FFN 32, causal mask, ~192-token input.
TA9 · serving the long sequence
This is the hard part — how do they serve O(10⁴) history at Homefeed latency?

A stack of systems tricks, each measured. This is a masterclass in the latency/throughput constraints from Part 2 (Q-C KV-cache, Q-E O(n²)):

Deep dive · addedUPP — Foundation Model, Conditional FM & CFM Scaling

Provenance. Internal Pinterest/UPP material, reconstructed from your notes plus the CFM design doc, the CFM architecture diagram, and the CFM model-scaling doc you provided. Most of my earlier guesses are now sourced; remaining genuine unknowns are marked ⚠. One correction from the first draft: CFM is the unified ranking model (FM backbone + TransAct v2 + feature cross); the CLR/UBR two-tower is the separate retrieval-side base model — both are kept below, clearly separated.

The frame: UPP = pretrain → fine-tune for Pinterest recsys

UPP (Unified P13N Platform) is a three-tier hierarchy — Foundation Model → Base Models (the CFMs) → Surface-specific models — so surfaces (Homefeed, Related Pins, Board-More-Ideas, Notifications, Search) fine-tune shared pretrained backbones instead of training from scratch. This is the BERT/GPT foundation-model transfer recipe (Part 2) applied to recommendation, motivated by compute efficiency (pretrain once, amortize across many FT runs) and larger, higher-quality cross-surface training data (especially hard negatives).

Foundation Model (FM)

FM1 · what it is (now sourced)
Architecture, inputs, and training objective of the FM.

The FM is a transformer over the recent-n user sequence, mapped through an ID embedding table, trained self-supervised with a next-token loss (ℒ_ntl — predict the user's next action). It's the bottom tier; its outputs are consumed by the ranking model above.

  • Per-token features (sourced): FM pretraining only has what's logged in the long sequence — omnisage (os), neardup id, action type, timestamp, fv type. Each sequence item carries ID features + action/fv-type features + pre-embedded features (the colored circles in the diagram).
  • Training data limit: FM pretrains on source-of-truth data that has no impressions logged — so it lacks the best hard negatives (impressions from well-ranked feeds), and they're hard to add cost-effectively.
  • Loss limit: FM has only the sequence future-action (next-token) loss. Consequence (the author's hard-won lesson): you can't train FM well with pointwise ranking losses — not enough candidate information and the negatives are too easy.
Connections: FM's next-token objective is the next-item objective from Part 2 (Q-B) and the generative-recsys frontier (Q-I), used as a pretraining task; lineage from PinnerFormer (Q-G). Note the symmetry with TransAct v2's Next Action Loss (TA8): NAL is the same future-action signal added as an auxiliary loss inside a ranker, whereas FM makes it the primary pretraining objective.

Conditional FM (CFM) — the unified ranking model

CFM1 · definition
What is Conditional FM, exactly?

CFM is a single ranking model that predicts engagement for a pin in any context — trained on and serving HF, Related Pins, Board-More-Ideas, Notifications, and Search. It's the cornerstone of UPP: a strong unified ranker that surface teams fine-tune. Per the doc, it "borrows its design from current ranking models" (which have converged over time), is based on the Foundation Model, and also uses TransAct v2 (16k long-seq modeling) plus other core-ranking innovations.

So, compositionally: CFM = FM backbone + TransAct v2 sequence module + feature cross + ranking heads, trained with future-action loss (on the FM component) + BCE ranking loss + pairwise loss (the diagram's ℒ_ntl and ℒ_pwl + ℒ_ce).

This is where Part 5 meets Part 6: TransAct v2 isn't a separate thing — it is CFM's per-surface sequence module (the "surface-specific embedding generation" box: 16k-NN + recent-m + surface sequences). And the red "conditional on candidate pin" tokens are literally the candidate early-fusion pattern from TransAct (TA2) / DIN target attention (Q-H) — the "condition" generalizes "candidate" across surfaces.
CFM2 · high-level design
Walk the architecture and the per-surface conditioning.

A ranking model with conditionally-triggered, per-surface context encoders (different components — FM, feature cross — may each need their own per-surface encoder), built on the Foundation Ranker backbone:

  • Sequence + interaction modeling: Foundation Ranking transformer + ID embeddings, plus the 16k (compressed when available) + real-time omnisage transformer = TransAct v2.
  • Feature cross over sage embeddings, transformer outputs, and optional context embeddings.
  • Per-surface context encoders don't share parameters (the P2P encoder only gets gradient from P2P rows). Context features per surface: Search = search sage emb; P2P = query-pin os + pinclip + id embedding; BMI = board os emb; HF = learned emb (no features).
  • Single-epoch training (to start) so the embedding table can update during both CFM pretraining and fine-tuning.
⚠ Notes: the doc references a "Foundation Ranker" backbone — possibly distinct from the pure FM; treat the FM↔Foundation-Ranker naming as not-fully-pinned. Xue Xia flagged that sequence formats differ across surfaces, which may cause issues. Exact transformer depth/width still not specified.
CFM3 · the Pinnability-Light insight
Why a trimmed feature set — and why does that enable a cross-surface backbone?

From the Pinnability Sequential (aka Pinnability Light) work: they ran a per-feature ROI test — (1) what does it cost to store/train/serve this feature + its internal representation, and (2) what's the metric win if you drop it and spend the saved cost on better training (more architecture, longer training, higher serving)? Result: many features have strongly negative ROI — primarily sparse vector annotation features. What's worth keeping:

  • Key metadata: request time, pin creation time, pin neardup id
  • Key sage features: omnisage, pinclip, etc.
  • Key user-sequence features
  • PinPerf / UserPerf scalar float/int features

The unlock: the trimmed feature set is natively present across all core-surface datasets (these features matter for every surface), so it (a) doesn't hurt performance on Pinnability alone and (b) avoids the feature-set coordination problem that normally makes any cross-surface backbone hard to ship. Hence the central proposal: a trimmed-feature cross-surface ranking model as the backbone for core rankers.

Connection: "drop hand-engineered sparse features, reinvest the budget in scale + training" is the scaling-law thesis (Part 1, Q#1) and the transformer-native, let-attention-do-the-crossing direction (AutoInt, Q-H) — stated as an explicit ROI argument. Prior art noted in the doc: Closeup Level Engagement Model, Jinfeng Rao's Cross-Surface Pretraining, and the productionized GULP Ranker v0 (a fine-tuned Pinnability).

CFM5 · deploying CFM into a surface
Minimal vs maximal adoption, and what must stay unified.
  • Minimal: keep only the surface-specific embedding generation + FM components, discard the rest — CFM acts as a module that produces embeddings fed into feature cross (exactly how FM is used today).
  • Maximal: keep the full CFM model; override the last layer to customize output heads + engagement loss; surfaces add features by adapting them into the CFM feature cross and/or surface-specific embedding generation.

What must be held identical across CFM pretrain ↔ surface fine-tune (the consolidation targets), in priority order:

P0FM model + architecturethe core reason to pretrain at all
P1TransAct architecturemajor quality lever; benefits from cross-surface data
P2Feature cross
P3Which features are used
P4Label weights / heads / taskchange as little as possible from prod per surface, to isolate consolidation effects

Dataset distribution is held fixed across PT/FT for maintenance simplicity. Connection: minimal→maximal is the same frozen-extractor → full-fine-tune transfer-learning dial from the earlier UPP adoption spectrum (and the PEFT methods in CFM6 make it compute-budget-aware).

CFM6 · why it works
The efficiency argument.
  • Compute efficiency: pretrain once, amortize across many fine-tune runs.
  • More data without quality loss: aggregating surfaces increases volume — especially hard negatives from impression data on well-ranked feeds — improving quality and scalability.
  • Training→serving compute migration: doesn't change per-model serving cost, but shifts surface training compute into shared pretraining. Useful because there's more headroom in serving than training efficiency right now — the current/SOTA hardware gap is larger in serving, smaller dtypes (fp8/fp4) are easier to land in inference, and many rankers score more candidates per request than typical (so more compute-per-candidate is available).

Retrieval-side sibling — CLR / UBR (the base retriever)

Distinct from the ranking CFM: the base retriever is UBR, a Conditional Learned Retrieval (CLR) two-tower model (5 surfaces at once) producing multi-head viewer embeddings + pin embeddings for HNSW ANN at serving (Part 3, Q-F). The viewer tower routes each surface to its own condition tower (uniform contract: CONDITION_TOKEN [B,256] → into the sequence transformer; CONDITION_FC [B,512] → into DHEN), then a ConditionedUserSequenceTransformer (user sequence + condition tokens → attention), then DHEN feature cross + L2-norm; the pin tower mirrors it. Loss = in-batch-negative multi-head. Condition-tower variants: MultiConditionSlotTower (HF), _ConcatConditionTower (BMI/Search), P2PConditionTower, NotifConditionTower; they share a condition_type_embedding table. Same condition-as-tokens trick as the ranking side — the retrieval and ranking CFMs are conditional in the same way, on different output tasks.

CFM Model Scaling — the in-flight research

From the scaling doc (Lawhon, Poska, Rajesh, He, Yang). Related: "Next-Gen Teacher Foundation Model," "Future of RecSys Models in 2026."

SC1 · the question
What's the central scaling bet, and the early signal?

Observation: conventional FM pretraining scale often fails to transfer to fine-tune metrics unless FT compute is also increased. Hypothesis (in-flight): CFM pretraining transfers better to ranking under a fixed FT compute budget.

Early signal: CFM pretraining yielded ~1% repin wins on both HF and BMI fine-tune jobs — without architecture scale-up and with similar FT compute. (Recall ~1% repin is a substantial production gain.)

Central question (FT compute held fixed): what is the scaling behavior of FM vs CFM, and does CFM-pretraining scale deliver superior transfer to ranking than FM at the same fixed FT budget? Success criterion: for a fixed FT budget, scaling CFM pretraining gives statistically significant FT-metric + online wins vs equivalently-scaled FM.

Connection: this is a scaling-laws study (Part 1, Q#1) reframed for recsys transfer — "does pretraining scale buy FT-metric gains at constant FT compute?" — exactly the predict-quality-before-you-train logic, applied to the PT/FT split rather than to a single model.
SC2 · constraints & distillation
What bounds the design, and how does distillation fit?
  • Training constraint: FT compute must be fixed (that's the whole point of the comparison).
  • Serving headroom: serving clusters have underutilized GPUs — bottlenecked on the host CPUs of GPU machines, so low SM activity — leaving inference headroom to spend on bigger/served models. (Ties to CFM6's "more compute per candidate.")
  • Distillation vs scaling: distillation targets larger architectures that can't be served online (e.g. they don't leverage request-level computation). It's complementary to student-model scaling: a non-serveable teacher can be made arbitrarily better, then distilled into a serveable student.
Connection: teacher→student distillation + embedding quantization is the model-compression / serving-efficiency theme — same family as TransAct v2's int8 quant + serving kernels (TA9, Q-C). Big non-serveable teacher → small serveable student is the recsys-specific twist (serveability, not just size, is the constraint).
SC3 · fine-tuning methods ablated
Under a fixed FT budget, which adoption strategies are being tested?

Each applied to both FM- and CFM-pretrained backbones at each scale point (optimizer/epochs/batch-size tuned only within the same FT budget):

  • Frozen + quantized embedding table + ablate dense/all-loss + scale-up batch size
  • Multi-epoch with smaller total dataset (may need multiple pretrain snapshots)
  • LoRA on selected blocks (LoRA and DoRA; SVD/PiSSA vs standard init)
  • Full FT under budget + embedding-table updates (<1 epoch)
  • LoRA + embedding-table updates
  • Frozen embedding table + partial FT (top-k transformer blocks)
  • Frozen embedding table + frozen FM (minimal, head-only FT)
  • Mixed: low-rank adapters + selective LayerNorm/bias tuning
  • LoRA on the embedding table

Hypotheses: (1) under fixed FT compute, CFM-pretraining scale beats FM-pretraining scale on transfer; (2) for larger backbones, partial/frozen FT (LoRA + frozen components) closes the gap to full FT within budget; (3) teacher–student or longer-context pretraining further improves CFM transfer at constant FT compute.

Connection: LoRA / DoRA / PiSSA are parameter-efficient fine-tuning (PEFT) — the compute-budgeted version of the minimal→maximal transfer dial (CFM5). The whole ablation is "how much of the backbone do I adapt, given a fixed budget" — transfer learning under an explicit FLOP constraint.
