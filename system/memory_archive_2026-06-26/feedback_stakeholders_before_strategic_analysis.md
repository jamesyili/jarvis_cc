When James asks for strategic analysis of a meeting, political dynamic, or multi-person scenario involving 3+ named stakeholders, read `work+self/people/stakeholders.md` BEFORE running the analysis — not during, not after correction.

**Why:** Session 2026-04-18c ran an RLHF meeting dynamics analysis that miscast Anna K as "Search-side framing" (actually Retentive Recs PM + James's Inner Circle work-bestie) and Matt Chun as "unknown — what's his domain?" (actually UPP PM reporting to Andrew, high-trust via shared UPP political battles). James had to correct both. Then mis-placed Rahul's org (Blending is under Dylan, not outside). Three corrections in one session for stakeholder context that was sitting in the file the whole time. Operating Principle 6 ("Stakeholder intelligence is live. Treat stakeholders.md... as active operating intel") exists precisely to prevent this — but I didn't trigger on it because the meeting composition wasn't framed as a "stakeholder task." It was framed as a strategic question, and I treated the stakeholders as variables to reason about rather than people with live profiles.

**How to apply:**

1. **Trigger recognition.** Any message that names 3+ stakeholders in a strategic or relational frame (meeting, coalition, org dynamic, promotion, communication plan) → stakeholders.md gets read first.
2. **Scope of read.** Use Grep for each named person; if any aren't in the file, flag to James before running analysis.
3. **What to verify explicitly:** role, reporting line, trust level, recent history, known coalition alignments.
4. **When unsure of a name/role, ASK — don't run analysis on guess.** Per Operating Principle 8 ("Don't guess — ask").
5. **When James corrects a stakeholder role**, treat it as signal that stakeholders.md may need an entry added or updated — proactively offer to add/update.
