Generation Mechanics

Training decides what a model knows; decoding decides what it does at serve time — and for generative retrieval, decoding is the retrieval algorithm. This lesson is the machinery under next week's TIGER deep-dive and the arithmetic under the GPU-serving conversation.

What this lesson changes: after ~60–75 min you can (1) explain each decoding strategy by what it trades, (2) run a beam search by hand and say precisely why beam ≠ greedy and why beams collapse onto shared prefixes, (3) compute KV-cache memory from the model config from memory, and (4) write the parameter count of any transformer from its config. Direct inputs: the W4–5 TIGER work, the GPU-serving push (this is calculation #1 and #8 of the agenda's Appendix C), and any "put an LLM in the serving path" proposal.

§2Sampling: one knob, three costumes

At each step the model hands you a distribution over the vocabulary. Everything in decoding is a policy for spending that distribution. Temperature rescales the logits before softmax: p_i ∝ exp(z_i / T). Top-k and top-p (nucleus) are truncations: sample only from the k most likely, or the smallest set covering probability p.

Bridge: temperature is the same dial as Boltzmann exploration in your bandit layers — one scalar trading exploitation (T→0: argmax, deterministic, maximally on-distribution) against exploration (T>1: flattened, tail gets real mass). For generative retrieval this is a diversity control you get for free, which the two-tower + ANN stack never had natively — ANN returns the same neighbors every time. Where it breaks: in recsys the "tail" you up-weight with high T isn't neutral — it's disproportionately low-quality and off-policy inventory, so temperature-as-diversity needs the same guardrails as any exploration budget. Uniform noise is not curated discovery.

§3Beam search, by hand

Greedy decoding takes the argmax at every step. Its failure is structural: a confident first token can lead to a mediocre sequence, and greedy can never back out. Beam search keeps the B highest-probability partial sequences (beams) and extends them all. For GR-SID with 3-code SIDs, retrieval = beam search of depth 3; the final beams are the retrieved candidates.

The two production consequences (both from W1, now visible mechanically): (1) Prefix collapse — high-probability beams tend to share prefixes (both survivors here could easily share code 0 with a slightly different table), so naive beam search retrieves near-duplicates; that is why PinRec built multi-token generation and why every GR-SID deployment carries an explicit diversity mechanism. (2) Invalid sequences — the model happily assigns mass to code combinations no item has. Constrained decoding masks each step's distribution to the children of the current prefix in a trie of valid SIDs, renormalizes, and guarantees every beam is a real item. Cost: a trie lookup per step; the latency question from W1's judging file ("does constrained decoding fit the budget?") is asking about exactly this loop.
Self-explain
Why does the invalid-sequence problem not exist in two-tower retrieval? One sentence.
Two-tower retrieval selects from an index that only contains real items — the candidate set is enumerated, not generated — whereas a decoder composes items token-by-token from a vocabulary, so "combinations that exist" is a constraint that must be imposed from outside (the trie). Generation trades an enumeration guarantee for compositional flexibility; constrained decoding buys the guarantee back at per-step cost.

§4The KV cache — what generation remembers

Autoregressive generation re-attends to the whole prefix at every step. Without caching, each new token recomputes K and V for every previous token in every layer — O(n²) recomputation of things that cannot have changed. The KV cache stores each token's K and V per layer at the moment it's produced; generating token n+1 computes exactly one new Q, K, V and attends against the cache.

KV bytes per token = 2 · n_layers · n_kv_heads · head_dim · bytes_per_value (2 = one K + one V)

Bridge: the KV cache plays the role of your precomputed candidate-side embeddings in two-tower serving — pay compute once, reuse across scoring. Where it breaks — and this is the recsys-shaped trap: candidate-side embeddings are global (computed once, shared by every request all day); a KV cache is per-user, per-request — user histories don't repeat across requests, so there is no cross-request reuse. LLM-serving economics leans hard on shared-prefix caching (system prompts); recommendation gets none of that for the user side. What recommendation gets instead is the M-FALCON trick: score N ranking candidates against one user's cached prefix — the cache amortizes across candidates within a request, not across requests. Any LLM-in-the-ranking-path proposal that quotes vanilla LLM serving benchmarks without this correction is quoting the wrong workload.

§5Why decode is the expensive half (30-second preview of W11)

Prefill (encoding the user history) processes all tokens in parallel — big matrix multiplies, compute-bound, cheap per token. Decode emits one token at a time, and each token must stream all model weights (plus the cache) through memory — bandwidth-bound. That asymmetry is the whole economics of serving: batch-1 decode speed ≈ memory bandwidth ÷ model bytes, and batching is the game. W11 does the full arithmetic; carry one number until then: a 1B model prefilling a 2K-token history costs ~8 ms on an H100 at 50% MFU — inside a ranking budget; a 70B the same way is ~560 ms — not.

§6Parameter counting — the exit skill

The config → parameter-count mapping, once, precisely (standard decoder, FFN expansion 4×, MHA):

Embeddings: V · d (tied output head: free; untied: + V · d) Per layer: Attention: 4 · d² (W_Q, W_K, W_V, W_O — each d×d) FFN: 8 · d² (d→4d and 4d→d) ≈ 12 · d² per layer (+ small: norms, biases) Total ≈ V·d + L · 12 · d² GQA note: with n_kv < n_heads, W_K and W_V shrink by n_kv/n_heads — attention becomes (2 + 2·n_kv/n_heads) · d²

A TIGER-style decoder: vocab = 3×256 codes + specials ≈ 1,024 · d = 512 · L = 8, tied. Parameter count?
Emb: 1,024 × 512 ≈ 0.5M. Layers: 8 × 12 × 512² ≈ 25.2M. Total ≈ 26M — and notice what the exercise just showed you: GR-SID models are tiny, because the SID vocabulary deleted the V·d monster (a 10⁸-item catalog at d=512 would be 51 billion embedding parameters). The entire capacity story of generative retrieval is visible in this one subtraction — the catalog's parameters moved out of the embedding table and into the RQ-VAE + the decoder's ability to compose codes.
